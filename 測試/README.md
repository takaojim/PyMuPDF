# PyMuPDF 初步使用心得：建築 PDF 圖面的向量與文字擷取

日期：2026-11-10

## 一、PyMuPDF 是什麼

PyMuPDF（`pip install pymupdf`）是用 Python 處理 PDF 的函式庫，底層是 MuPDF 引擎，速度很快。主要功能有：

- 讀取文字，可以帶座標、字型、字高（`page.get_text("dict")`）
- **抽出向量圖形**，包括線段、矩形、曲線、顏色、線寬（`page.get_drawings()`）
- 抽出嵌入的點陣圖、辨識表格（`page.find_tables()`）
- 把頁面渲染成圖片（`page.get_pixmap(dpi=...)`）
- 編輯 PDF：註解、浮水印、合併、拆分，以及在 PDF 上繪圖

授權是 AGPL。事務所內部使用沒問題；要做成產品對外提供，需要開源或購買商業授權。

## 二、測試的圖面

- A1 圖紙、1:100，地下一層平面圖，由 Revit/CAD 輸出（Adobe PDF Library）
- 全部是向量：約 3.5 萬條路徑、5.8 萬段線段，沒有點陣圖
- 原本的 CAD 圖層（OCG）在輸出時已經沒了，但**顏色和線寬都還在**

## 三、做了什麼、結果如何

| 項目 | 做法 | 結果 / 驗證 |
|---|---|---|
| 比例確認 | 量軸線 1 到 7 的 PDF 距離，和標註 4180 cm 比對 | 1 pt ≈ 3.528 cm，確認是 1:100 |
| 室名面積表 | 從文字座標配對「室名 / 面積 / 房號 / 床數」，輸出 Excel | 60 個空間，合計 **1186.66 ㎡**、**40 床**，和圖上的檢討表完全一致 |
| 依顏色和線寬分圖層 | 以「顏色_線寬」分類 | 粗黑線（1.42）是牆柱，紅藍點鏈線是軸線和投影線，灰細線是家具設備 |
| 只留牆柱 | 只留下粗黑線，重繪成新的 PDF | 得到一張乾淨的牆柱圖 |
| 轉成 DXF | 用 ezdxf 換算成 cm、翻轉 Y 軸，依分類建立圖層 | AutoCAD 可以直接開，尺寸是 1:1 的真實大小 |

程式：`demo.py`，用法是 `py demo.py "圖.pdf" 輸出資料夾`。預設比例 1:100，其他比例請改 `SCALE`。

## 四、踩到的坑

1. **Windows 的 `python` 指令是 Microsoft Store 的空殼**，執行會失敗。要改用 `py`（Python Launcher）。
2. **腳本不要取名 `inspect.py`**，會和 Python 標準庫撞名，`import pymupdf` 時會出錯。
3. **文字配對要看實際座標**：床數「【4床】」是寫在房號右邊同一行，不在面積下面。第一次跑出來床數是 0，看了座標才修正。
4. **虛線和點鏈線會被拆成很多小段**，所以 DXF 偏大（約 11 MB）。→ 已在第二階段用 `pdf2dxf_clean.py` 解決，見第七節。
5. **PDF 只有「線」，沒有語意**：哪條是牆、哪條是門，要自己用線寬、顏色、位置來判斷。
6. **掃描檔不適用**：只有 CAD 直接輸出的向量 PDF 才抓得到線條。

## 五、最重要的心得：讓 Agent 寫腳本，不要讓它當工具

> 該計算的就要用腳本，該讀資訊的時候就要用腳本，它的工作是做腳本，不是把自己當工具在用。

- **錯的做法**：讓 AI 自己讀 PDF 文字、自己心算加總，結果可能漏看、算錯，也沒辦法驗證。
- **對的做法**：讓 AI 寫程式去讀、去算，再用圖上的檢討表交叉驗證。

這次的實例：

- 面積和床數是程式算出來的，再和圖上的檢討表比對，數字吻合，才算數。
- 床數第一次算錯，是看了程式的輸出才發現並修正。如果是 AI 自己讀，可能不會察覺。
- 比例是用量測驗證出來的，不是猜的。

腳本留下來就是事務所的工具，換一張圖可以重跑，結果也一樣。

跟 Agent 下指令時可以這樣說：

- 「請**寫腳本**統計所有房間的面積，不要自己讀了再算。」
- 「算完之後，請用另一種方式**驗證**，例如跟圖上的檢討表比對。」

## 六、之後可以發展的方向

- 一整套圖批次產出面積表，並檢查每張的加總是否和檢討表一致
- 新舊版圖面自動比對，標出改過的地方
- 法規檢核，例如每床面積、走廊寬度
- 用線寬和顏色統計牆的長度或構件數量
- 把 DXF 連結進 Revit，再自動建立軸線和牆（可以搭配 Revit MCP）

## 七、第二階段：用 ezdxf 整理 DXF（`pdf2dxf_clean.py`）

> 圖面檔案（PDF / DXF / PNG / JPG / XLSX）屬於實際案件資料，**不放進 git**（見 `.gitignore`），這裡只保留程式和筆記。

### 分工

- **PyMuPDF**：讀 PDF，取出文字和向量。
- **ezdxf**：讀、寫、修改 DXF。它**不會讀 PDF 內容**：DXF 裡的 `PdfUnderlay` 只是貼附 PDF 當底圖的參考；ezdxf 也能把 DXF 輸出成 PDF 或 PNG，但都不是讀 PDF。
- 「PDF 和圖面交叉比對」就是把兩者接起來，再用 Python 比對。

### 用法

```
py pdf2dxf_clean.py 圖面.pdf 輸出資料夾 [--scale 100] [--unit cm|mm] [--no-grid-origin]
```

輸出三個檔案：

- `*_整理.dxf`
- `*_整理_預覽.png`：用 ezdxf 從 DXF 重新畫出來，用來跟 PDF 對照
- `*_整理報告.txt`：各圖層處理前後的數量、線型、軸線間距

### demo.py 的 DXF 有什麼問題，怎麼解決

| 問題 | 原因 | 做法 |
|---|---|---|
| 58,925 條獨立 LINE | Revit 匯出 PDF 時把虛線和弧線拆成小段 | 共線又相接的段合併，首尾相連的串成 LWPOLYLINE，最後 **11,198 個圖元**，檔案從 11 MB 降到 3.9 MB |
| 虛線碎成小段 | PDF 的 `dashes` 屬性都是實線，虛線在匯出時就拆開了 | 依每層的間隙容許值接回整條線，並**量測**原本的長段、間隙、點的長度，自動建立 7 種 DXF 線型。例如軸線是長 36、空 9、點 9、空 9（pt） |
| 同一段線疊 2 到 3 次 | Revit 匯出時疊線 | 端點取到 0.01 pt 後去除重複 |
| 灰色牆柱填充不見 | 填充路徑只被轉成邊線 | 轉成實心 HATCH（313 塊） |
| 圖層名稱是 `黑_w1.42` | 只依顏色和線寬命名 | 把每一組顏色和線寬單獨畫出來，看過內容後取名，例如 `A-牆柱-輪廓`、`S-軸線`、`A-家具設備`，共 22 層；對照表在 `LAYER_MAP`，可以自己改 |
| 中文可能顯示成「?」 | 預設字型 | 建立「中文」文字樣式，字型用 msjh.ttc 微軟正黑體，並保留文字旋轉角度 |
| 貝茲曲線形狀錯 | `add_spline(控制點)` 會把控制點當成曲線要通過的點 | 改成先把曲線切成多段直線再畫 |
| 原點在紙張左下角 | — | 以**軸線 1 / A 交點**為原點，座標和建築軸線一致，方便匯入 Revit |
| 遮罩、視圖框混在圖裡 | Revit 匯出的白色遮罩和裁切框 | 放到 `X-遮罩`、`X-視圖框` 圖層，預設關閉 |

### 還沒解決 / 要人工確認

- 部分圖層的用途是推測的，報告裡有標「推測」，例如 `C-地界線`、`A-範圍線`、`A-開口範圍`、`A-上方投影線`。如果不對，改 `LAYER_MAP`。
- 虛線畫成的弧線（例如門扇軌跡）還是一小段一小段的，目前只會接直線。
- 圖框上寫的是「A2-03 1FL-建築平面圖」，和檔名裡的「地下室」不一致，要確認是哪一張。
- 這次在 AutoCAD 裡實際打開 DXF 的結果還沒確認。目前只在 ezdxf 裡驗證過：稽核 0 錯誤，預覽圖和 PDF 一致。

### 這一階段的「腳本 vs 自己當工具」實例

| 不好的做法：AI 自己做 | 這次的做法：寫腳本 |
|---|---|
| 看圖估算虛線長度 | 程式量出每一段長度和間隙，再自動歸納成線型 |
| 用眼睛判斷比例 | 程式算軸線間距，再和圖上的尺寸逐一核對 |
| 一條一條判斷五萬條線 | 寫規則讓程式分類、去重複、合併 |

AI 只有一步是用看的：把每一組顏色和線寬畫成圖，判斷是牆還是家具。這種需要「理解」的判斷才交給 AI，而且結果在報告裡**標明是推測**，讓人確認。
